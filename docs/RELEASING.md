# Preparing and publishing TrackPeek

The release helper prepares local artifacts. It does not commit, push, publish, install the app, or notarize it.

## Version and source

Set MARKETING_VERSION and CURRENT_PROJECT_VERSION in project.yml, regenerate the Xcode project, and add or update docs/releases/<version>.md. The build number must exceed every distributed build number: Sparkle compares CFBundleVersion, not just the display version. Version 1.0 uses build 1; 1.1 originally shipped as build 3 and its localized refresh uses build 4. Build 2 was not published.

Review README.md, CHANGELOG.md, and the product roadmap. Run the app tests, release-script tests, and git diff checks described in [CONTRIBUTING.md](../CONTRIBUTING.md). Commit the verified source in focused commits before creating a public tag.

## Local artifacts

Prerequisites: Xcode, XcodeGen, the configured app-signing certificate, and the existing Sparkle key matching SUPublicEDKey. No signing key is exported or generated by the script.

```sh
./script/release.sh 1.1 4
```

The script requires the arguments to match project.yml and refuses to reuse an existing release directory. It builds Release for arm64 and x86_64, checks both the app and its helper, verifies code signatures, creates the ZIP, embeds release notes, signs the update archive, and verifies the generated appcast and checksums. Archive verification uses CryptoKit and SUPublicEDKey from the built app; it does not read the private key from Keychain again.

Output in .build/release/1.1/:

| File | Purpose |
| --- | --- |
| TrackPeek-1.1-build4.zip | Universal app archive for this exact build |
| appcast.xml | Sparkle feed with the archive signature and embedded notes |
| SHA256SUMS | Checksums for the archive and feed |
| TrackPeek-1.1-build4.txt | Plain-text notes embedded in the feed |

Archive and notes names include the build number: `TrackPeek-<version>-build<build>.zip` and `.txt`. The enclosure for build 4 uses https://github.com/Komortes/TrackPeek/releases/download/v1.1/TrackPeek-1.1-build4.zip. SUFeedURL remains the latest release's appcast.xml. Do not rename an archive after preparing it: the generated feed and checksums refer to its exact name. Preserve failed or previous artifacts by moving the release directory before a rebuild.

Public ZIP archives are immutable. The original `TrackPeek-1.1.zip` is build 3 and stays available for recovery. A higher build with the same display version gets a new archive name and its own source tag; it does not replace the previous ZIP or rewrite a public tag.

The checked-in signing setup uses Apple Development with hardened runtime. The archive is not notarized. Keep that limitation in the install instructions and release notes; do not describe it as Developer ID distribution.

## Publishing a new display version

After the repository owner authorizes publishing, push the verified source and choose its exact commit SHA as the release target. Ensure it is an ancestor of main before publishing. For a display version with no existing public release, create a draft using `gh release create`, the verified SHA as `--target`, the build-specific ZIP, appcast.xml, SHA256SUMS, and the corresponding release notes. Do not let GitHub create a tag against an unrelated or stale default branch.

Review the draft, target, assets, signing limitation and release notes. Download and verify the draft before making it the latest stable release. An unpublished draft may be corrected with `gh release upload ... --clobber`; first inspect its status and ensure any existing tag already names the verified source. Never rewrite a public tag.

## Refreshing 1.1 with build 4

The repository owner has authorized this same-version refresh. Keep the public `v1.1` tag at the original build 3 source, preserve `TrackPeek-1.1.zip`, and record the new source with `v1.1-build4`. The release page remains `v1.1`; its notes explicitly distinguish the two archives.

1. Inspect the existing release, tag and assets. Save its current appcast.xml, SHA256SUMS and release metadata locally so the feed can be restored if needed. Confirm that build 4 has a higher CFBundleVersion and that its source includes the localization changes.
2. Push the verified release commit. Create and push `v1.1-build4` at that exact SHA, without force or moving `v1.1`.

```sh
# Set this to the verified, pushed build 4 source commit, not a branch name.
RELEASE_COMMIT='<verified commit SHA>'
git tag v1.1-build4 "$RELEASE_COMMIT"
git push origin refs/tags/v1.1-build4
```

3. Upload the new ZIP without replacing any existing archive. Download that public asset into a fresh directory and check its SHA-256, Sparkle signature, bundle versions, universal app/helper binaries and code signatures against the prepared artifact.

```sh
gh release upload v1.1 .build/release/1.1/TrackPeek-1.1-build4.zip \
  --repo Komortes/TrackPeek
```

4. Update SHA256SUMS and the release notes, including the build 4 source tag, the build 3 recovery archive and the signing limitation. Upload **appcast.xml last**, only after the new public ZIP has passed verification. This is the point at which Sparkle starts offering build 4.

```sh
gh release upload v1.1 .build/release/1.1/SHA256SUMS \
  --repo Komortes/TrackPeek --clobber
gh release edit v1.1 --repo Komortes/TrackPeek \
  --title 'TrackPeek 1.1' --notes-file docs/releases/1.1.md --latest
gh release upload v1.1 .build/release/1.1/appcast.xml \
  --repo Komortes/TrackPeek --clobber
```

5. Download the current ZIP, appcast.xml and SHA256SUMS into a fresh temporary directory and run `shasum -a 256 -c SHA256SUMS`. Check that `latest/download/appcast.xml` redirects to 1.1 and contains build 4 and its exact build-specific archive URL. Verify that both source tags still point to their intended commits and that the build 3 archive is unchanged.

Confirm update discovery from 1.0 and 1.1 build 3 using a separate test installation without replacing personal preferences. An archive signature check alone does not verify the complete installer flow. Test the downloaded build in English and Ukrainian, including Settings and onboarding; relaunch after changing the macOS per-app language.

If publication is interrupted, inspect `gh release view v1.1` and the actual downloaded feed before retrying. Reuse a new ZIP only when its bytes match the verified local artifact; never clobber it with different contents. If the new feed has not been uploaded, existing update checks still use the previous feed. Keep v1.0 and the build 3 archive available for manual recovery; publishing an older feed does not safely downgrade an installed build 4. Any further fix needs a higher build number and a new immutable archive, with another explicitly authorized refresh or a new display version.

References: [Sparkle publishing and build numbers](https://sparkle-project.org/documentation/publishing/) and the bundled generate_appcast, sign_update, and generate_keys help output.
