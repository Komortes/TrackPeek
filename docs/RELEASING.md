# Preparing and publishing TrackPeek

The release helper prepares local artifacts. It does not commit, push, publish, install the app, or notarize it.

## Version and source

Set MARKETING_VERSION and CURRENT_PROJECT_VERSION in project.yml, regenerate the Xcode project, and add docs/releases/<version>.md. The build number must exceed every distributed build number: Sparkle compares CFBundleVersion, not just the display version. Version 1.0 uses build 1; 1.1 uses build 3, superseding its earlier unpublished build 2.

Review README.md, CHANGELOG.md, and the product roadmap. Run the app tests, release-script tests, and git diff checks described in [CONTRIBUTING.md](../CONTRIBUTING.md). Commit the verified source in focused commits before creating a public tag.

## Local artifacts

Prerequisites: Xcode, XcodeGen, the configured app-signing certificate, and the existing Sparkle key matching SUPublicEDKey. No signing key is exported or generated by the script.

```sh
./script/release.sh 1.1 3
```

The script requires the arguments to match project.yml and refuses to reuse an existing release directory. It builds Release for arm64 and x86_64, checks both the app and its helper, verifies code signatures, creates the ZIP, embeds release notes, signs the update archive, and verifies the generated appcast and checksums. Archive verification uses CryptoKit and SUPublicEDKey from the built app; it does not read the private key from Keychain again.

Output in .build/release/1.1/:

| File | Purpose |
| --- | --- |
| TrackPeek-1.1.zip | Universal app archive |
| appcast.xml | Sparkle feed with the archive signature and embedded notes |
| SHA256SUMS | Checksums for the archive and feed |
| TrackPeek-1.1.txt | Plain-text notes embedded in the feed |

The enclosure uses the immutable version URL https://github.com/Komortes/TrackPeek/releases/download/v1.1/TrackPeek-1.1.zip. SUFeedURL remains the latest release's appcast.xml. Preserve failed or previous artifacts by moving the directory before a rebuild; do not replace assets belonging to an existing public release.

The checked-in signing setup uses Apple Development with hardened runtime. The archive is not notarized. Keep that limitation in the install instructions and release notes; do not describe it as Developer ID distribution.

## Publication

After the repository owner authorizes publishing, push the verified source and choose its exact commit SHA as the release target. Ensure it is an ancestor of main before publishing. Do not let GitHub create a tag against an unrelated or stale default branch.

```sh
# Set this to the verified, pushed release commit, not a branch name.
RELEASE_COMMIT='<verified commit SHA>'

gh release create v1.1 \
  .build/release/1.1/TrackPeek-1.1.zip \
  .build/release/1.1/appcast.xml \
  .build/release/1.1/SHA256SUMS \
  --repo Komortes/TrackPeek \
  --target "$RELEASE_COMMIT" \
  --title 'TrackPeek 1.1' \
  --notes-file docs/releases/1.1.md \
  --draft
```

Review the draft, target, assets, signing limitation, and release notes. Publish it as the latest stable release only after that review:

If an unpublished draft already exists, inspect its status first, update its target to the verified pushed SHA, and replace its assets with `gh release upload ... --clobber`. Replace assets only while the release is a draft. Check that an existing tag, if any, already names the verified source; do not rewrite a public tag. Download and verify the updated draft before publishing it.

```sh
gh release edit v1.1 --repo Komortes/TrackPeek --draft=false --latest
```

Download the published ZIP, appcast.xml, and SHA256SUMS into a fresh temporary directory and run shasum -a 256 -c SHA256SUMS. Check that the latest/download/appcast.xml redirects to 1.1 and contains build 3 and the immutable archive URL. Confirm update discovery from 1.0 using a separate test installation without replacing personal preferences. An archive signature check alone does not verify the complete installer flow.

If publication is interrupted, inspect gh release view v1.1 before retrying. Keep v1.0 available for manual recovery; releasing an older build does not safely downgrade existing installations. Fixes after publication get a new version and higher build number.

References: [Sparkle publishing and build numbers](https://sparkle-project.org/documentation/publishing/) and the bundled generate_appcast, sign_update, and generate_keys help output.
